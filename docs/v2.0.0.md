# v2.0.0: planned removals

What 2.0.0 removes or renames, and what 1.x does about it in the meantime. Everything here still works in 1.x.

## Deprecated (users are warned)

These log a warning at build time (`useLogger('jade').warn` in `src/module.ts`) and are marked `@deprecated` or "deprecated" in the types and the README.

### `cursor.cursors` → `cursor.defaultCursors`

- **1.x:** `cursors` is copied into `defaultCursors` (`src/setup/customize-theme.ts`).
- **2.0:** remove the `cursors` field from `CursorConfig` (`src/shared/types/cursor.ts`), the copy in `customize-theme.ts`, the warning in `module.ts`, the test "deve aceitar o nome antigo `cursors`" and the README note under Cursor.

### Flat color theme format in `color.themes`

The pre-variant format: `summerSale: { dark: false, primary: '#FF8A00' }`, and built-in themes overridden by variant id (`dark: { primary }`).

- **1.x:** converted to the grouped format by `mergeColorThemes`/`normalizeColorThemes`, warned about by `findDeprecatedThemeEntries` (`src/shared/utils/merge-themes.ts`).
- **2.0:** accept only `{ light: {...}, dark: {...} }`. Remove `isLegacyThemeEntry`, `legacyOverrideMode`, `findDeprecatedThemeEntries` and their branches, `ThemeColors` from `ThemeEntry` (`src/shared/types/colors.ts`), the note in `ColorOptions.themes` and the README section "Flat format (deprecated)".

## Removed without a warning

### The fire cursor images

`src/runtime/public/images/ui/cursor/` (`cursor.png`, `cursor-hand.png`, `cursor-text.png`), referenced by `customCursor.defaultCursors` in `src/shared/theme.json` (marked `_deprecated` there).

- **2.0:** delete the images and empty the module's `defaultCursors`. Projects that want image cursors set their own.
- **To decide before removing:** with no default images, `'base'` means the system cursors, so the module's own `themeCursors.venix: 'base'` would show them on the Venix theme. Probably switch it to `'themed'`, or drop the entry. The drawn cursors' fallback also becomes the system cursor instead of the image. Also update the README (Cursor section, the `defaultCursors` description) and the tests that expect `/images/ui/cursor/cursor.png`.

## Planned renames

### `venixTheme` → `venixJade`

The config key (`configKey` in `src/module.ts`) and the `useVenixTheme`/`VenixThemeSwitcher` naming. The full naming map still needs approval before any code.

- **1.x:** accept both config keys, warning on `venixTheme`.
- **2.0:** only `venixJade`.
- **Never rename** the cookies (`venix-theme-preference`, `venix-theme-mode`, `venix-theme-resolved`) or the `venix-cookie-consent` storage key: visitors would lose their saved theme and consent.

### Built-in theme names in English

The keys of `colors.themes` in `src/shared/theme.json`, and the variant ids derived from them. The translations (`pt-BR`/`en-US`) don't change.

| Theme | Variant ids today | 2.0 |
| --- | --- | --- |
| `carnaval` | `carnaval-light`, `carnaval` | `carnival` |
| `pascoa` | `pascoa-light`, `pascoa-dark` | `easter` |
| `natal` | `natal-light`, `natal` | `christmas` |
| `halloween` | `halloween-light`, `halloween` | unchanged |
| `venix` | `light`, `dark` | unchanged |

The dark variant ids aren't consistent today (`carnaval`, `natal` and `halloween` have no `-dark` suffix, `pascoa-dark` does), so settle the id pattern in the same change.

What the names reach, so each needs a plan:

- **Saved preferences:** `venix-theme-preference` stores the theme name and `venix-theme-resolved` the variant id. Map the old values to the new ones when reading them (`normalizeThemeSelection` in `src/shared/utils/theme-resolver.ts`), or visitors lose their saved theme.
- **Project config:** overrides in `color.themes`, `color.defaultColor` and `cursor.themeCursors` keyed by the old names. In 1.x, accept the English names as aliases and warn on the Portuguese ones.
- **`data-theme`, the `<html>` class and the Vuetify theme names:** they're the variant ids, so projects' own CSS (`[data-theme='natal']`) and `useTheme()` calls in Vuetify stop matching. List them in the release notes.
- **Docs and tests:** the README examples and the tests that use `carnaval`, `pascoa` and `natal`.

### `--color-*` → `--jade-*` (CSS variables and UnoCSS classes)

The color variables are generic names: `--color-primary`, `--color-background`, `--color-scheme`, `--color-inverse`. Other color systems use the same prefix (Vuetify's `--v-theme-*` doesn't, but design systems, utility kits and a project's own CSS do), so a name can clash with another one and silently change a color. Moving everything under `--jade-*` removes that for good: nobody else is called Jade, and if someone is, the overlap is rare enough to ignore.

- **Variables:** `--color-<name>` → `--jade-<name>` for the old model: `--jade-primary`, `--jade-background2`, `--jade-scheme`, `--jade-inverse`. The semantic tokens already use `--jade-*` (`--jade-bg-subtle`, `--jade-text-primary`, `--jade-fill-primary`) since they were added, with no alias period.
- **UnoCSS:** the token classes already are `jade-bg-subtle`, `jade-text-muted`, `jade-fill-primary`. The preset's old-model colors (`bg-primary`, `text-primary`…) keep their class names and only point at the new variables.
- **1.x:** emit both, `--jade-*` first and `--color-*` as aliases of it (`--color-primary: var(--jade-primary)`), and document `--jade-*` as the name to use. A CSS variable can't warn at build time the way a config key does, so the deprecation lives in the README and the release notes.
- **2.0:** only `--jade-*` and `jade-*`.
- **What it reaches:** the generated CSS (`src/shared/css/colors.ts`, `tokens.ts`), `useVenixTheme().tokens.cssVar()`, the `<VenixThemeSwitcher>` fallbacks of the old model, the UnoCSS preset (`unocss-preset.ts`), the README, the playground's `--pg-*` aliases and the tests that assert the names. Projects' own CSS that reads `var(--color-primary)` stops matching, so the release notes list it. `color-scheme` itself is a real CSS property and doesn't change.
- **Not touched:** the Vuetify theme colors (JS keys, no CSS variable of ours) and the cookies (see the `venixJade` rename above).
- **To decide with it:** the other generic prefixes the module emits, `--cursor-*` (`--cursor-pointer`…), could move to `--jade-cursor-*` in the same release. `--venix-switcher-*` already has its own prefix.
- **Done for the tokens:** they use `--jade-*` and `jade-*` from the start, because they were unreleased when the prefix was settled. Only the old model's `--color-*` still needs the alias period.

### The module's public files under their own path

`src/setup/register-assets.ts` serves `src/runtime/public` at the site root (`baseURL: '/'`): `/fonts/Iceberg/...` and `/images/ui/cursor/...`. A project with its own files at those paths collides with them, and they're served even with typography and the cursor off.

- **2.0:** serve them under a prefix of their own (e.g. `/_jade/`), and only for the modules that are on. Update the paths in `src/shared/theme.json` (`typography.customFonts`, `customCursor.defaultCursors`, though the cursor images are removed anyway) and the tests that expect them. Projects that point at `/fonts/Iceberg/Iceberg-Regular.woff2` themselves need the new path, so it goes in the release notes.

### The semantic tokens become the only color model

The built-in themes ship `tokens: true` in 1.x, next to the old model, so both work until 2.0 (decided together with the `--jade-*` prefix).

- **2.0:** remove the old model: `background2`/`background3` and the `--color-*` variables (with their `--jade-*` aliases), the `ThemePalette` slots that only the old model used, and the old-model fallbacks (`--pg-*` in the playground, the switcher's fixed palette, the scrollbar's `background2`/`3` defaults).
- **Vuetify:** in 1.x the built-in themes' default tokens stay out of Vuetify (`ColorsConfig.defaultTokens`, `src/setup/customize-theme.ts`, `register-vuetify.ts`), so its text on `primary` doesn't change under existing projects. In 2.0 delete `defaultTokens`: Vuetify then gets `on-primary`, `on-secondary`, `surface`, `on-surface` and `on-background` from the tokens. Release notes: the text on a Venix red button turns black (5.25:1) where Vuetify chose white (4.0:1).
- **Contrast check:** the build skips the built-in themes' default tokens (a seed can't reach 7:1 at `'AAA'` and the project can't change it). Drop that filter together with `defaultTokens`.
- **`experimental`:** it only extends the tokens to the project's own themes (and to Vuetify). With `tokens` the default for every theme it has nothing left to do: remove the option, or keep `tokens: false` as the opt-out.
- **Neutral surfaces:** the built-in Venix lifts `bg-subtle`/`bg-muted` a step (`tokens` overrides in `theme.json`) to stay close to its old `background2`/`3`; with the old model gone it can drop those overrides if the default look is preferred.

## Candidates (not deprecated yet)

Kept for compatibility today. Decide whether to deprecate them in a 1.x release first, so users get a warning before 2.0.

- **`theme.toggle(name?)`** (`useVenixTheme`): kept for compatibility, superseded by `theme.set()`, `mode.set()` and `mode.toggle()`.
- **A theme `icon` as a plain string**: called the legacy format in `ColorOptions.iconFormat` and `resolveThemeIcon`, but still documented as valid in the README.
- **Legacy cookie values** (`normalizeThemeSelection` in `src/shared/utils/theme-resolver.ts`): a theme cookie holding a variant id (`'dark'`, `'carnaval'`) or the old `'system'`. Removing this resets the saved theme of visitors who haven't come back since the theme/mode split, so it may be worth keeping.
